# M06 — identity, organization, audit and worker migration

Canonical source: ARCHITECTURE.md §§2.2–2.3, 5, 17, 38, 41–46. Java25/Spring Boot4, Hibernate/JPA aggregate writers and PostgreSQL18; no Python application dependency.

## Implemented scope

- `identity`: current-branch membership list; typed role/activation change request; two distinct active owners request/approve; self changes prohibited; version and expected authorization epoch checked. Applying increments epoch so the existing API membership/epoch boundary rejects old tokens. The IdP remains responsible for global logout, MFA, password recovery and refresh-token revocation.
- `audit`: append-only scoped audit entity/public module API and authenticated audit register. Identity request/application and the named outbox projection append evidence. It is not yet instrumentation of every platform command.
- `company`, `branch`: current-scope organization reads. They do not provision tenants, create companies/branches or permit scope switching by headers.
- `workers`: bounded manual drain of named `audit-projection-v1` consumer. PostgreSQL delivery rows retain owner, token, lease expiry, attempts and retry time. Row locks/SKIP LOCKED claim work; completion checks fence and live lease. Audit effect and inbox receipt commit together; retry is delayed. The consumer projects informational facts, never posts sales/stock/money again.
- V8 adds typed request/audit tables, forced RLS, immutable audit trigger and narrow membership updates with database request/maker-checker guards. It changes membership row visibility from self-only to current branch; identity read APIs independently require active-owner authority. No SECURITY DEFINER or unrestricted membership mutation is used.

## API

| Method/path | Permission and payload |
|---|---|
| GET `/api/v1/identity/members` | `identity:manage`; actual active owner in current branch |
| GET `/api/v1/identity/changes` | Same; latest 100 requests |
| POST `/api/v1/identity/changes` | `{operationId,targetActor,desiredRole,desiredActive,expectedEpoch,reason}`; matching Idempotency-Key |
| POST `/api/v1/identity/changes/{id}/approve` | `{operationId,version}`; matching Idempotency-Key; a different owner approves; same approval operation replays without applying twice |
| GET `/api/v1/companies`, `/api/v1/branches` | Authenticated active scope; results limited by RLS |
| GET `/api/v1/audit` | `audit:read`; latest 200 current-scope events |
| POST `/api/v1/operations/outbox/project-audit` | `operations:manage`, active owner; `{limit:1..100}`; source-event inbox makes repeated drains idempotent |

The existing global API filter requires X-Request-ID for mutation requests. Standard `SCOPE_` OAuth authorities and direct permission claims are accepted by HTTP permission checks. The service rechecks actual database owner membership for identity and drain operations. Neither merchant nor platform identity can expand scope through arbitrary request IDs.

## Remaining work — not represented as complete

Tenant provisioning, invitations/identity-provider lifecycle, current-policy MFA/step-up enforcement, single-owner emergency recovery, custom role permission design and access-review UI remain outstanding. This initial operation requires two existing owners; it does not invent a second identity or silently bypass maker-checker. Permission claims after role changes must be reissued by the configured IdP; the epoch makes existing claims unusable, not automatically rewritten.

Imports/exports, backup/PITR orchestration, support access, retention/privacy workflows and notification transport are not migrated in this assignment. No placeholder module or success response is provided for them. This worker is an explicitly invoked scoped informational consumer, not the complete background-worker supervisor, ordered economic consumer, DLQ/replay console, global tenant dispatcher or external delivery transport. Complete operation-result expiry/reconstruction and cursor pagination remain pending.

The whole platform is not complete; these source paths and executed cases are a bounded migration increment.
