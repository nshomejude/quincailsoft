# M03 — Java finance, cash, deposits and mobile-money migration

Binding references: architecture §§2.2–2.3, 3.2, 3.4, 8.2–8.3, 32, 36–38. No Python service is called by these modules.

## Implemented source

- `finance`: trusted module API for balanced journal posting and period locks, sale receivable balances, row-locked receipt allocation, and explicit receivable/customer-credit split for return credit. Integral XAF throughout; an excess receipt is rejected rather than hidden by capping a negative balance.
- `tenders`: scoped cash-session opening, cash receipts against recognized customer debt, deposit collection, deposit-to-sale allocation without another cash receipt, approved cash deposit refunds and cash-session reconciliation. Expected till cash derives from immutable tender facts and the declared opening float. Cash activity changes the session version; stale close reviews fail. A variance is posted to explicit cash-overage/shortage accounts. Closed shifts are immutable.
- Every tender command uses stable tenant operation identity, exact request hash, immutable response replay, authoritative current scope, a reason and a transaction containing its cash/receivable/deposit/journal/outbox effects. Database constraints prevent deposit over-consumption and immutable tender facts.
- `integrations`: MTN credential-token/request-to-pay/status transport. Approved HTTPS origins only, redirects disabled, configured target environment, explicit production activation, positive exact amounts, reference/external-ID/currency/payer checks and a financial transaction reference required for verified status. Sandbox verification never posts XAF or a journal.
- Durable MTN intents are committed QUEUED before transport; UNKNOWN is committed before dispatch. Ambiguous retry queries the same reference instead of submitting a new charge. Verified provider truth is committed before accounting reconciliation; closed periods or changed receivable allocation leave PROVIDER_VERIFIED_REVIEW for retry without charging again. Provider financial references are unique. Confirmed posting writes a provider-clearing/AR journal and outbox fact atomically.
- `expenses`: typed draft, submission, independent approve/reject, cancellation and approved cash payout through the tender public API. Payout, immutable cash fact, balanced journal and outbox commit atomically; stale versions and insufficient cash fail. Bank payouts are not fabricated.
- `finance` period workflow: typed create and independently approved close/reopen proposals, preserved request and decision reasons, version conflict checks and canonical replay. Closure holds the period lock and requires installed cash/provider/expense/return guards. Open tills, unresolved live collections, review/approved expenses and approved unposted returns block closure. Runtime raw period status updates require a same-transaction independent approved request. Company public API locks branch metadata; multi-branch companies fail closed until dedicated authority is implemented.
- Intent responses omit phone, credentials and raw provider bodies. Callback hints, when invoked by a future callback adapter, only flag reconciliation; they do not settle money. Public callback routing is not yet enabled.

## Runtime setup

MTN requires `QUINCAI_MTN_USER_ID`, `QUINCAI_MTN_CREDENTIAL`, `QUINCAI_MTN_SUBSCRIPTION_KEY`, `QUINCAI_MTN_ENVIRONMENT`. Sandbox origin defaults to the official sandbox; production requires the explicitly merchant-confirmed `QUINCAI_MTN_ORIGIN` and `QUINCAI_MTN_LIVE_ENABLED=true`. Cameroon migration status must be confirmed with the merchant account manager. Configuration flags do not establish provider acceptance.

REST routes and DTOs are declared by `TenderService`, `TenderController`, `MobileMoneyService`, `ProviderController`, `ExpenseService`, `ExpenseController`, `PeriodService` and `PeriodController`. Reads require scoped cash/tenders read authority; refunds and cash management have distinct permissions. No endpoint permits manual Mobile Money confirmation. Intent reconcile uses the persisted intent identity and safely queries the same provider reference on retry; it intentionally does not create a new operation ID. Expense writes use expenses:write/approve/pay and periods use periods:manage/approve; read permissions remain separate, including cash:read for payout selection.

## Remaining required migration

Orange Money remains unavailable until the subscribed Cameroon merchant transaction contract is supplied and verified. No undocumented country API was substituted. Real MTN sandbox/live acceptance, signed callback ingress/rate controls, scheduled provider-outbox consumer binding, provider refunds/fees/settlement, secret rotation and deployment encryption controls remain unverified.

Bank confirmation/reconciliation, supplier advances/payments, journal reversal, multi-branch period-close authority and statutory mapping remain incomplete. Expense/period forms were wired by the web migration agent; full integrated browser acceptance remains root-owned. Receipt/deposit document issuance requires integration with the document service; tender records are operational facts, not certified fiscal receipts. Cash opening is a declared float and requires production custody/preceding-shift policy before pilot certification. No phase or whole finance module is certified complete by this document.
