# M09 — isolated platform administration and public storefront

This migration slice implements two separate Next.js 16.4.6 / React 19.3.1 / TypeScript applications and typed Java 25 / Spring Boot 4 services. It is **not completion of the canonical platform-control, subscriptions or commerce modules**. The existing architecture remains authoritative.

## Executable scope

| Surface | Implemented behavior |
| --- | --- |
| `apps/platform-admin` | Separate operator sign-in, Redis-backed server sessions, onboarding-request list, request form, independent-review approval form, sign-out and failure state. |
| `apps/merchant-storefront` | Public store catalogue at `/{slug}`, public listing detail at `/{slug}/{id}`, missing-store/item states and service-failure state. No fabricated inventory count or functioning checkout is shown. |
| Java `platform-control` | Typed `/admin/onboarding` list/create and `/{id}/approve`; enrolled operator registry; independently verified platform issuer/audience; separate maker/checker; optimistic versions and exact operation replay. Approval records `APPROVED_FOR_PROVISIONING`, without creating a tenant or identity membership. |
| Java `commerce` | Owner-authorized store settings and publication of an explicit catalogue snapshot; tenant-scoped JPA aggregates; idempotent mutations and transactional outbox; public DTO containing only approved public fields. |
| Java `subscriptions` | Read-only COMMERCE entitlement gate provisioned by a privileged deployment process. Runtime requests cannot enroll operators, grant entitlements or charge subscriptions. |

## Trust and data boundaries

- Platform security is enabled only with `quincai.platform.enabled=true` and separately configured `quincai.platform.issuer` / `quincai.platform.audience`. Reusing either merchant value fails startup. `/admin/**` has a separate security chain; the merchant fallback denies these paths even if platform security is disabled. The main API integrates that fallback.
- Platform subjects must be UUIDs enrolled in `platform_operator` by a privileged deployment process. Token scopes alone cannot manufacture a platform operator. The scoped transaction verifies active enrollment. Platform requests never derive tenant membership from browser headers.
- Platform browser configuration uses `PLATFORM_APP_URL`, `PLATFORM_API_URL`, `PLATFORM_OIDC_*` and its own OIDC client. The cookie is `quincai_platform`; Redis session/login keys use `quincai:platform:`. Authorization uses code flow, PKCE, state and nonce. Tokens stay server-side. Mutations verify request origin and carry an idempotency operation identifier.
- Public storefront server requests use only `PUBLIC_CATALOG_API_URL` and `/api/public/stores/{slug}`. There is no merchant bearer token, tenant header, database connection or generic table API in the storefront.
- Public catalogue DTOs contain a slug, public store name, random publication identifiers, explicitly reviewed title/description, unit and exact XAF price string. Private product identifiers, tenant/company/branch identifiers, private SKU, source name, costs, balances and customer contacts are excluded.
- Publication copies a source catalogue price and unit rather than accepting a browser-supplied price. Currently only active zero-tax products can be published; tax-inclusive price-policy support is still required for taxable products. Subsequent private catalogue edits do not silently republish.
- Private publication aggregates use forced PostgreSQL RLS. Public projections have narrowly granted read permissions; projection writes are performed by fixed-schema database triggers. Runtime roles cannot directly forge the projections.
- An active, unexpired COMMERCE entitlement is required for publication. A separate opaque public gate immediately removes revoked/expired catalogues from the public API. The gate contains no tenant identifier or billing information. Its backing subscription entitlement is tenant-scoped and cannot be granted by runtime roles.
- Product availability is explicitly “Confirm availability with the merchant.” Checkout state is `CHECKOUT_NOT_ENABLED`. No order, reservation, collection, payment confirmation or fulfillment is fabricated.

## API contract

| Method/path | Authorization and effect |
| --- | --- |
| `GET /api/v1/commerce/store` | Merchant `commerce:manage` scope and active owner membership; current branch store settings. |
| `POST /api/v1/commerce/store` | Same, matching `Idempotency-Key`, expected version and reason; enable additionally requires active COMMERCE entitlement. |
| `GET /api/v1/commerce/listings` | Same merchant scope/ownership; current store's private publication settings. |
| `POST /api/v1/commerce/listings` | Same, matching operation header, expected version and reason; publish additionally requires entitlement and safe source-price policy. |
| `GET /api/public/stores/{slug}` | Anonymous, approved public projection only, active publication gate; unknown/disabled/unentitled stores absent. |
| `GET /admin/onboarding` | Platform issuer/audience, `platform:tenants:read`, enrolled active operator. |
| `POST /admin/onboarding` | Platform write scope, enrolled operator, `Idempotency-Key`, `X-Request-ID`, explicit name and reason. |
| `POST /admin/onboarding/{id}/approve` | Platform approve scope, enrolled operator different from requester, expected version and matching operation identifier. |

All these modules share the canonical backend; neither Next app implements financial posting. The platform Next app defaults to port 3200; storefront to 3300. Environment examples are checked in beside each application. Start these apps after the shared pnpm install; provision actual identity-provider and Redis configuration before sign-in.

## Validation

- Both Next production builds completed successfully, including TypeScript validation and route generation.
- `PostgresCommerceIntegrationTest` exercises production JPA code against real PostgreSQL as a non-owner `NOBYPASSRLS` role: owner rejection, tenant isolation, projection-write denial, source/identifier non-disclosure, exact prices beyond JS safe integers, immutable operation replay, explicit publication, unpublish/disable, and entitlement denial/revocation/expiry.
- `PostgresPlatformIntegrationTest` exercises production JPA code against real PostgreSQL with separate enrolled operators: unknown/revoked operator denial, self-approval denial, independent approval, exact replay before/after review, and no tenant or membership provisioned.
- Root reports a successful 28-module Maven `verify`, including both real PostgreSQL M09 tests, full Boot signed-JWT application startup and Modulith verification. Final aggregate evidence belongs in the root migration validation report. Tests intentionally require `QUINCAI_PG_TEST_URL` and are skipped without it. No mocked database or successful checkout fixture substitutes for that evidence.

## Remaining canonical work

Full tenant provisioning and suspension, audited privileged support sessions, dedicated environment orchestration, approved domains/certificates, subscription plans/contracts/invoices/renewals/limits, platform charge collection, durable administrative audit-event delivery, and the full platform detail/report suite remain pending. The current onboarding review is a prerequisite record, not a provisioning engine.

Cart, stock reservations, payment attempts and compensation, merchant MTN/Orange checkout integration, customer order tracking, fulfillment/delivery, refund handling, storefront merchant legal pages, image storage, SEO/sitemaps/structured data, consent, localization, rate limiting and fraud controls remain pending. Public storefront deployment therefore still requires an operational readiness review; the catalogue slice alone does not satisfy the complete commerce acceptance gate.

The applications currently use typed server-rendered forms and a small shared visual style. They do not certify the full canonical design-system, reporting, workflow or screen inventory. No production deployment or live-money operation was performed in this slice.
