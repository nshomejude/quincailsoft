# Subscription billing implementation checkpoint

Specification: ARCHITECTURE §§5.4, 8.10, 24.1–24.2 and N02/N11. This is a new SaaS capability, not a replacement for merchant payment-provider or POS settlement logic. Parent integration lead runs and records executable evidence; no test pass is claimed by this document.

## Implemented boundary

- `POST /admin/billing/invoices` issues a typed, immutable subscription invoice or a credit note referencing an original invoice. Integral XAF subtotal, discount and tax reconcile using checked arithmetic. Issuer, customer, jurisdiction, description and billing-period snapshots are retained.
- Platform operations require a signed scope and a currently enrolled active operator. Credit corrections additionally require `platform:billing:credit` and a different operator from the original invoice issuer. Replays recheck current authority and enrollment.
- Invoice and durable billing event are persisted together through JPA; an event failure rolls back invoice creation. Global operation locking rejects changed payloads/actors and concurrent repeated requests retain one original receipt. Independent original-invoice locking prevents concurrent credits exceeding original net or tax.
- Platform invoice listing requires `platform:billing:read`. Merchant listing requires `billing:read` (raw or SCOPE authority), matching authenticated actor, active owner/finance membership in the current tenant/company/branch, and the current authorization epoch. Historical invoice reads have no billing-expiry gate.
- Forward migration V25 uses tenant composite invoice references, forced RLS, actor-attributed insert-only runtime grants and immutability triggers. A PostgreSQL trigger independently enforces original-issuer separation, identity snapshot matching and serialized net/tax credit conservation. No merchant journal, AR/AP, sale, tender or cash record is changed.
- Forward migration V28 adds immutable plan versions (new plan code for revised commercial terms), trial bootstrap, current subscription versions, cancellation, explicit trial/paid-term expiry, independently reviewed notice/contract attestations and immutable lifecycle command receipts. Read snapshots immediately display elapsed trials and paid terms as EXPIRED even before the explicit expiry command persists that transition. Bootstrap has a public API for onboarding and materializes selected commerce entitlements. Mobile access is included in every plan. Runtime inserts cannot fabricate an ACTIVE subscription; paid activation requires a reviewed receipt.
- `requireAllowed` uses persisted, same-version, independently reviewed notice and contract evidence with an elapsed grace period. Subscription and notice rows remain locked inside the caller's transaction. READ, EXPORT, RECONCILE, BACKUP and STATUTORY_ACCESS are never blocked by this billing policy. Missing contracts on legacy/perpetual tenants do not infer SaaS billing restrictions. Economic-command integration belongs to the API-server boundary.
- Manual bank reconciliation records an invoice allocation, bank reference and evidence SHA-256. Another enrolled operator must approve. Receipts are explicitly `MANUALLY_RECONCILED`, never provider-verified. Partial receipts do not activate a subscription. Fully reconciled, uncredited calendar-month invoices matching the selected plan price can activate or renew a paid term; future terms require explicit activation when their start date arrives. Immutable invoice-consumption records prevent reactivation via another partial receipt or after cancellation.
- EN/FR escaped HTML invoice, credit-note and independently reconciled receipt printing is available through platform and authorized merchant endpoints. Responses use private/no-store caching, nosniff, no-referrer and restrictive CSP. Pending bank evidence cannot be printed as a receipt.

## Acceptance authored

`PostgresSubscriptionBillingTest` exercises real PostgreSQL invoice creation, exact totals, unchanged replay, changed-payload and other-actor conflict, separate credit operator, net/tax credit limits, overflow, RLS, immutable facts, atomic rollback, six concurrent same-operation requests, competing credits, current role and epoch, revoked platform replay and zero merchant economic writes. `PostgresSubscriptionLifecycleTest` covers trial bootstrap, quota comparisons, notice/reviewer/grace controls, retained historical access, manual partial/full reconciliation, rejected underpriced activation, consumed-invoice replay, merchant printing and revoked review replay. `SubscriptionRestrictionPolicyTest` covers the billing policy; `SubscriptionHtmlTest` covers hostile text escaping and pending-receipt rejection.

## Not complete

- Invoice numbers are unique `SUB-UUID` / `SUB-CN-UUID` platform references. Jurisdiction-specific sequential fiscal numbering, numbering audits, legally reviewed invoice templates and tax calculation rules are not implemented or certified. The caller supplies tax explicitly; these fields do not establish tax compliance.
- Automated payment-provider/webhook verification and subscription-fee refund settlement remain external integration gaps. A credit note is an accounting correction, not a refund-success assertion. Recorded bank evidence is manually attested; the application cannot establish authenticity of the external bank artifact from a supplied hash alone.
- Automatic activation currently requires the exact configured monthly plan price, no discount or credit, and a complete calendar month. Prorated terms and independently approved commercial price overrides require additional explicit contracts; an underpriced invoice cannot upgrade a tenant. Full usage metering and reservation-backed quota enforcement are not implemented. `requireAllocation` only compares trusted caller counts with limits and must not be described as concurrent quota enforcement.
- Durable billing events are not a dispatch worker. Notice delivery is recorded with evidence and independently reviewed; it is not verified provider delivery. Automated delivery/retry integrations remain outstanding.
- Lists are bounded to 100 records; cursor pagination and full historical export remain outstanding. Frontend and browser evidence is maintained by the platform UI/integration assignments, not asserted here.
- Full HTTP issuer/audience-chain verification and final integration remain with the shared API integration tests; these focused service/database tests cannot certify production readiness.
